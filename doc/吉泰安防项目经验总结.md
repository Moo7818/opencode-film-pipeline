> 基于 2026-06-15 ~ 2026-06-22 项目全流程实战记录

## 一、管线流程经验

### 1.1 stages.json 命名与标准管线的映射

**问题**：`stages.json` 中的阶段名称与 `AGENTS.md` 定义的标准管线（6阶段）名称不一致。

| 标准管线阶段名 | stages.json 中的名称 | 问题 |
|---------------|---------------------|:----:|
| 项目初始化 | 前期设定 | 名称不同 |
| 监制提取设定 | 角色场景道具设计 | 名称和覆盖范围不同 |
| 全局视觉资产生成 | — | stages.json **缺失此阶段** |
| 拆解分镜 | 分镜制作 | 基本对应 |
| 剧集级参考图 | — | stages.json **缺失此阶段** |
| 视频生成 | 视频生成 | 对应 |
| — | 后期合成 | 标准管线无此阶段 |
| — | 输出交付 | 标准管线无此阶段 |

**教训**：stages.json 和管线定义应保持同步。如果 stages.json 缺失"全局视觉资产生成"和"剧集级参考图"这两个阶段，流程会跳过关键步骤。建议在项目初始化时由 coordinator 严格按标准管线生成 stages.json。

**建议**：统一阶段命名，或让 coordinator 创建 stages.json 时直接以标准管线为模板。

### 1.2 阶段推进流程

标准阶段推进链路：

```
Orchestrator 识别意图
  → spawn Coordinator 推进 stages.json
  → Coordinator 更新当前阶段为 completed，下一阶段为 in_progress
  → Orchestrator spawn 对应子 Agent 执行业务
  → 子 Agent 完成 → 返回产物清单
  → Orchestrator spawn Coordinator 注册产物
  → Coordinator 注册 manifest + 事件
  → 循环下一阶段
```

**关键规则**：
- 只有 Coordinator 可以推进 `stages.json` 的阶段流转
- Coordinator 写文件后必须调用 `validate.py` 校验 JSON 语法
- 阶段一旦 `completed` 不可回退
- 每个 `stage.transition` 必须记录到 `events.jsonl`

## 二、角色设定与参考图管理

### 2.1 监制角色映射错误

**问题**：原始剧本中角色名和参考图命名可能不一致，监制（Producer）容易错误关联。

在吉泰安防项目中：
- 剧本角色：爸爸（吉小泰）、妈妈、**女儿**（无名）
- 参考图文件：`吉小泰_基准.png`、**`吉小美_基准.png`**
- 监制错误地**将吉小美映射为"女儿"**

**原因**：Producer 看到"吉小美_基准.png"，按文件名推测"吉小美"是剧中女儿角色，但实际吉小美是另一个独立角色（本集未出场），而女儿另有其人。

**教训**：
- 原始剧本才是角色定义的**唯一可信源**，参考图文件名只能辅助参考
- 需要人工确认角色与参考图的对应关系
- 剧本中没有名字的角色（如"女儿""妈妈"）不应自动与有名字的参考图绑定

**改进建议**：
- Producer 在提取角色设定时，先基于剧本确认角色清单，再匹配参考图
- 增加检查机制：如果角色名在剧本台词中没有出现，发出警告

### 2.2 全局级 vs 剧集级参考图的区分

| 类型 | 用途 | 存储路径 | 生成时机 |
|:----:|------|---------|---------|
| **全局级** | 角色的标准形象基准（通用的、跨集的） | `全局依赖/角色参考图/` | 阶段3（全局视觉资产生成） |
| **剧集级** | 基于分镜的本集专属形象（特定服装/表情/动作） | `EP{xx}/角色参考图/` | 阶段5（剧集级参考图） |

**经验**：角色可以先在剧集级生成，再提升为全局级。如妈妈和女儿最初只有 EP01 集参考图，后来通过复制到 `全局依赖/角色参考图/` 的方式提升为全局资产。

```
cp EP01/角色参考图/妈妈_EP01集.png → 全局依赖/角色参考图/妈妈_基准.png
→ 注册为 character_ref 到 manifest
```

### 2.3 参考图注册到 manifest 的流程

所有生成的图片必须注册到 `manifest.json`：

```bash
# 使用 register-artifact.ps1 脚本
& ".opencode/skills/project-coordinator/scripts/register-artifact.ps1" `
  -ManifestPath ".meta/projects/{uuid}/manifest.json" `
  -EventsPath ".meta/projects/{uuid}/events.jsonl" `
  -Type "character_ref" `
  -Name "妈妈_全局角色参考图" `
  -ArtifactPath "project/吉泰安防/全局依赖/角色参考图/妈妈_基准.png" `
  -Stage "角色场景道具设计" `
  -ProjectId "{uuid}"
```

图片文件使用 `--fast` 指纹（基于 mtime+size）而非完整 SHA-256，避免大文件 I/O 开销。

## 三、画风统一管理

### 3.1 全局设定的重要性

**问题**：项目初期没有全局设定文件，角色/场景/道具的 prompt 中画风描述不一致。

**解决方案**：创建 `全局依赖/全局设定/项目全局设定.md`，集中定义：
- 项目定位（安全科普教育宣传片）
- 画风定义（皮克斯/迪士尼3D卡通风格）
- 角色/场景/道具各自的风格约束
- 画面构图规则（9:16竖屏）
- 叙事风格

**效果**：所有子 Agent 在生成参考图任务表时，prompt 中统一注入画风描述。

### 3.2 画风注入模式

实践中最有效的 Prompt 注入模式：

1. **任务表顶层**：`model: "gpt-image-2"`，`imageSize: "1K"`
2. **每个 task 的 prompt 头部**：`"3D卡通渲染，Pixar/Disney卡通美学"`
3. **主体描述中**：`"皮克斯风格卡通化造型，轮廓柔和圆润"`
4. **prompt 尾部**：`"超高品3D渲染，抛光玩具质感"`
5. **末尾固定**：`"服装上没有任何文字、logos、标签或文字标识，no text，no logo"`

## 四、道具造型一致性

### 4.1 共用硬件的道具冲突

**问题**：两个道具参考图使用了同一硬件设备（平板电脑），但渲染时可能采用不同设计，导致视觉冲突。

| 道具 | 展示内容 | 冲突原因 |
|:----:|---------|:---------|
| 平板手机 | 平板物理设备（正面/背面/侧面/俯视） | — |
| 家庭安全隐患自查清单 | 同款平板+屏幕内容 | ⚠️ 硬件造型可能不一致 |

**解决方案**：让"家庭安全隐患自查清单"改为 **纯屏幕 UI 特写**，不展示平板硬件本体，彻底消除冲突。

**教训**：
- 如果两个道具共享同一物理载体，应统一设计或让其中一个专注于内容/UI
- 任务表 prompt 中明确区分"物理设备"和"屏幕内容"两种展示方式
- 生成前检查所有共用设备的道具提示词是否一致

## 五、图像生成实践

### 5.1 任务表 JSON 格式（基于 art-director 规范）

```json
{
  "model": "gpt-image-2",
  "tasks": [
    {
      "model": "gpt-image-2",
      "imageSize": "1K",
      "aspectRatio": "16:9",
      "filename": "输出文件名.png",
      "images": ["参考图路径（可选）"],
      "prompt": "完整提示词..."
    }
  ],
  "output_path": "输出目录/"
}
```

**规范要点**：
- `images` 数组放参考图路径（全局级基准图），可为空
- `aspectRatio`：角色/道具用 `16:9`（四视图/六视图排版），场景用 `2:1`（俯瞰+三宫格）
- `filename` 需与任务表所在目录区分
- prompt 中明确标注**图例排版方式**（四视图/六视图/俯瞰+三宫格）

### 5.2 多任务并行提交

art-director 支持并发提交 + 自动轮询 + 本地下载 + OSS 持久化。一次提交多个 task 可提高效率。

**注意**：
- API 额度不足时会返回 `"apikey credits not enough"`
- API 端点路径需与服务器实际路由一致（`/v1/api/generate` vs `/v1/images/generations`）
- 图片文件用 `--fast` 指纹注册到 manifest

### 5.3 参考图路径映射

```
角色参考图：project/{name}/全局依赖/角色参考图/{角色名}_基准.png
场景参考图：project/{name}/全局依赖/场景参考图/{场景名}.png
道具参考图：project/{name}/全局依赖/道具参考图/{道具名}.png
剧集级：   project/{name}/EP{xx}/角色参考图/{角色名}_EP{xx}集.png
```

## 六、分镜生成经验

### 6.1 推荐使用配置文件模式

`run_pipeline.py --build --config` 避免 PowerShell 引号转义问题：

```json
// pipeline_config.json
{
  "pipeline_dir": "project/吉泰安防/EP01/.pipeline",
  "output_dir": "project/吉泰安防/EP01/分镜",
  "output_groups": "分组",
  "system_file": "project/吉泰安防/EP01/temp/system_prompt.txt",
  "user_file": "project/吉泰安防/EP01/temp/user_message.txt",
  "shard": false,
  "script_path": null
}
```

```powershell
python ".opencode/skills/storyboard-generator/scripts/run_pipeline.py" --build --config pipeline_config.json
```

### 6.2 use_storyboard_images 控制

通过 `project_config.json` 中的 `use_storyboard_images` 字段控制是否生成分镜图：

- `false` → 不追加 `--with-task-table` 参数，仅生成分镜 JSON
- `true` → 追加 `--with-task-table`，生成分镜图任务表供 art-director 出图

### 6.3 分镜产出结构

```
EP{xx}/分镜/
├── 分镜脚本.json          ← 场级完整 JSON
└── 分组/                  ← 独立组 JSON（每个组自包含通用设定）
    ├── 组1.json
    ├── 组2.json
    └── ...
```

**验证要点**：
- 每组 JSON 都包含 `通用设定` 字段（来自场级注入）
- 镜号连续无跳号
- 分组数量合理（本项目中 EP01 约 60 秒 → 24 组）

## 七、Agent 协作模式关键规则

### 7.1 Orchestrator 行为约束

| 规则 | 说明 |
|:----|------|
| **禁止直接执行业务任务** | 所有文件操作、代码编写、数据生成通过 `task` spawn 子 agent |
| **禁止调研** | 不读文件、不搜索、不联网——这些是子 agent 的职责 |
| **职责链** | 识别意图 → 匹配阶段/子 agent → spawn → 汇总结果 |
| **快速分发** | 不要"先了解一下情况"，立即匹配并 spawn |

### 7.2 子 Agent 职责边界

| Agent | 负责 | 不负责 |
|-------|------|--------|
| Producer | 读剧本、多模态分析、联网检索、提取设定 | 不读 stages.json、不注册 manifest |
| Coordinator | 管理 stages.json、注册产物、推进阶段 | 不读产物内容 |
| character-director | 生成角色参考图任务表 | 不出图（由 art-director 执行） |
| art-director | 执行所有生图任务 | 不分析图像内容 |
| storyboard-director | 调用 run_pipeline.py | 不自造 JSON |

### 7.3 跨 Agent 数据流

```
Orchestrator → Producer → [角色/场景/道具设定]
Orchestrator → Coordinator → [更新 stage + 注册产物]
Orchestrator → character-director + prop-maker + set-designer → [任务表 JSON]
Orchestrator → art-director → [PNG 图片]
Orchestrator → storyboard-director → [分镜 JSON]
Orchestrator → Coordinator → [注册产物 + 推进阶段]
```

## 八、常见问题速查

| 问题 | 表现 | 解决 |
|:----|:----|:-----|
| 角色名映射错误 | 监制误将参考图角色当作剧本角色 | 以剧本台词为唯一可信源 |
| stages.json 缺少阶段 | 某些步骤被跳过 | 标准化 stages.json 生成模板 |
| 道具造型冲突 | 两个道具共用硬件但设计不同 | 一个展示硬件，一个展示内容/UI |
| API 余额不足 | `"apikey credits not enough"` | 充值或更换密钥 |
| API 端点 404 | MCP server 路径不匹配 | 确认 `grsai_client.py` 中端点路径 |
| 图片指纹注册 | 大文件哈希计算慢 | 使用 `hash.py --fast` 快速指纹 |
| PowerShell 引号转义 | prompt 含特殊字符被错误解析 | 使用配置文件模式（方式A） |

## 九、后续优化建议

- [ ] **统一 stages.json 与标准管线的阶段名称**，避免映射混乱
- [ ] **Producer 增加角色名校验**：检查剧本台词中是否出现角色名，避免映射错误
- [ ] **全局设定模板化**：新项目初始化时自动创建全局设定骨架文件
- [ ] **多道具一致性检查**：产出参考图前自动检测共用硬件的道具 prompt 是否一致
- [ ] **API 端点可配置**：将 API 端点路径抽到配置文件中，便于切换环境
- [ ] **分镜质量评估**：建立分镜 JSON 的自动化质量评分标准
- [ ] **画风注入模板库**：维护常用画风的 Prompt 代码片段，子 Agent 直接引用
