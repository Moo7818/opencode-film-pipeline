# 交付中心蓝图

## 现状分析

当前系统中的子 agent 是职责高度专一的流水线节点，并非根据任务自动判断 skill 加载的通用型 agent。

### 当前架构

```
opencode.json
  └── agent { … }           ← 内联 prompt（角色定义 + 核心约束）
         ↓
  skill 工具按需加载 SKILL.md  ← 详细操作手册
```

agent 与 skill 是两层结构，prompt 定义人设，SKILL.md 是知识库。两层各自维护，有冗余和同步成本。

## 目标范式

**核心等式：sub-agent = skill**

一个 skill = 一个可以独立运行的 agent。不再区分 agent prompt 和 skill 文档，合二为一。

### 范式三层

```
经理（一次性引导者）
  └── 加载元 Skill → 询问项目背景 → 生成交付中心
         ├── opencode.json（agent 定义，自动从 SKILL.md 生成）
         ├── AGENTS.md（通用规则）
         ├── SOP 文档（orchestrator 的 prompt）
         └── 目录骨架
      完成后经理退出

Orchestrator（常驻调度者）
  └── 加载 SOP 文档 → 按阶段路由 → spawn sub-agent → 推进

Sub-agent（每个 = 一个 skill 实例）
  └── SKILL.md 自包含：角色声明 + 操作规范
```

### 关键角色定义

| 角色 | 生命周期 | 职责 |
|------|---------|------|
| **经理** | 一次性，构建完成即脱离 | 加载元 Skill，收集项目背景，生成交付中心文件 |
| **Orchestrator（主管）** | 常驻 | 加载 SOP 文档，按阶段路由，spawn sub-agent，推进管线 |
| **Sub-agent（事业部）** | 常驻 | 每个 sub-agent = 一个 skill，有独立的角色声明和操作规范 |

### 特点

- **标准化**：所有 skill 遵循统一 frontmatter 格式，可被元 Skill 自动识别和组装
- **可复用**：skill 库即 agent 库，跨项目可复用，无需重复定义
- **可长程**：Orchestrator 按 SOP 持续推进，不丢失上下文
- **可跟进**：子项目分布式推进，独立交付

## SKILL.md 标准化

为实现 sub-agent = skill，每个 SKILL.md 需在 frontmatter 约定以下字段：

```yaml
---
name: project-coordinator      # skill 唯一标识
role: 你是 Coordinator，是子 Agent，执行者  # 角色身份声明，用作 agent prompt
mode: subagent                  # primary / subagent
description: 管理项目全生命周期…  # 描述，用作 agent description
---
# 以下为操作规范正文
```

元 Skill 可据此字段直接生成 opencode.json 中的 agent 定义：

```json
"coordinator": {
  "description": "（来自 frontmatter.description）",
  "mode": "（来自 frontmatter.mode）",
  "prompt": "{file:.opencode/skills/project-coordinator/SKILL.md}"
}
```

## 元 Skill（bootstrap）

元 Skill 是交付中心的入口，其名暂定 `delivery-center-bootstrap`。

### 工作流程

```
用户请求 → 经理加载 delivery-center-bootstrap
       ↓
1. 收集项目背景
   - 项目类型（影视/游戏/文档/…）
   - 规模与复杂度
   - 需要哪些 skill（core / optional）
   - 画幅、分辨率等基础参数
       ↓
2. 组建团队
   - 从 skill 库中选择必须的 sub-agent（core）
   - 根据项目背景选择可选的 sub-agent（optional）
   - 为每个 sub-agent 确认 SOP
       ↓
3. 生成交付中心文件
   - opencode.json → 自动从 SKILL.md frontmatter 生成 agent 定义
   - AGENTS.md → 全局通用规则（Python 环境、文件操作等）
   - SOP 文档 → orchestrator 的 prompt（阶段路由、推进规则）
   - 目录骨架 → project/、.meta/ 等
       ↓
4. 交付中心就绪
   - 经理退出
   - orchestrator 接手，加载 SOP 继续推进
```

### 变更流程

交付中心需要大幅改造时（如调整团队结构、更换 SOP），才需要重新召回经理。

## 待设计问题

1. **SOP 是否独立为 skill？**
   当前 orchestrator prompt 是 `.opencode/rules/orchestrator.md`。如果 SOP 也变成一个 skill（如 `sop-standard-pipeline`），orch 加载该 skill 来运行流程，则实现"一切皆 skill"的统一体系。

2. **元 Skill 的产出机制**
   元 Skill 通过什么方式生成文件？直接通过文件工具写入，还是通过模板渲染？

3. **skill 库的发现机制**
   经理如何知道有哪些 skill 可用？需要扫描 `.opencode/skills/` 目录并读取每个 SKILL.md 的 frontmatter。

4. **经理的具体实现**
   经理是一个 primary agent 还是独立脚本？是常驻在 opencode 配置中还是按需启动？

## 架构约束：信息流控制与权限隔离

### 问题发现

Orchestrator（调度者）不应加载或读取子 agent 的技能文件（SKILL.md）。否则会导致：

1. **上下文污染**：Orchestrator 的 prompt 上下文中塞入大量不应由它处理的细节（子 agent 的操作步骤、文件格式）
2. **职责退化**：Orchestrator 从"调度"退化为"替子 agent 写操作说明书"，spawn 的意义被稀释
3. **信息过载**：每多一个子 agent，Orchestrator 的上下文就膨胀一次

### 核心原则

> **Orchestrator 不读子 agent 的技能文件。**
>
> 它只需要知道三件事：
> - 谁负责什么阶段（路由表）
> - 给它什么参数（WHAT）
> - 不问它怎么做（HOW 由子 agent 自己的技能负责）

### 技术方案：opencode permission 系统

利用 opencode 框架的 per-agent permission 机制，在架构层面阻断信息流：

```json
{
  "agent": {
    "orchestrator": {
      "permission": {
        "read": {
          ".opencode/skills/**": "deny",
          "*": "allow"
        }
      }
    }
  }
}
```

这确保 Orchestrator 无法通过 `read` 工具读取任何技能文件。若要进一步阻断 `skill` 工具加载技能，可加：

```json
{
  "agent": {
    "orchestrator": {
      "permission": {
        "read": {
          ".opencode/skills/**": "deny",
          "*": "allow"
        },
        "skill": {
          "project-coordinator": "deny",
          "roles-ref-generator": "deny",
          "prop-ref-generator": "deny",
          "scene-ref-generator": "deny",
          "art-director": "deny",
          "storyboard-generator": "deny",
          "video-director-libtv": "deny",
          "producer": "deny"
        }
      }
    }
  }
}
```

### 与蓝图三层架构的关系

此约束强化了"交付中心蓝图"中三层架构的信息隔离：

```
经理（一次性引导者）         ← 可读所有 skill（构建阶段）
  └── 生成交付中心后退出

Orchestrator（常驻调度者）    ← 禁止读 skill（运行时）
  └── 只读 SOP 文档 + 路由表
       ↓ spawn（传 WHAT 不传 HOW）
Sub-agent（事业部）           ← 只读自己的 SKILL.md
  └── 每个 skill 自包含操作规范
```

### permission 完整能力对照

| permission key | 控制对象 | 支持 per-pattern | 当前状态 |
|---|---|---|---|
| `read` | `read` 工具 | ✅ 支持 glob | 已对 orchestrator 锁闭 `.opencode/skills/**` |
| `skill` | `skill` 工具 | ✅ 支持 glob | 待配置 |
| `edit` | `write`/`edit`/`apply_patch` | ✅ 支持 glob | 全局已配置 |
| `bash` | `bash` 工具 | ✅ 支持 glob | 全局已配置 |
| `task` | spawn 子 agent | ✅ 支持 name glob | 未启用 |
